# GitHub setup: git hooks, workflows, issue and PR templates for user projects

## Intent

`github/` is not this repository's CI. It holds templates for the projects
ai-stones sets up. A project set up with `ai-stones init` should end up with a
local harness that includes:

- git hooks that run the project's own checks on commit and push;
- GitHub Actions workflows in `.github/workflows`, runnable locally with act
  through the workflows tool, so the existing `workflows` hook can gate merges
  and publishes;
- issue templates and a pull request template.

These files are generated by Claude, guided by skills, from the project's
detected stack — not copied verbatim by the CLI.

## Goals

- `init` asks which workflows to generate, from a catalog (zero or more):
  `ci`, `release`, `security` (actionlint + zizmor + dependency review),
  `dependabot`. Nothing is preselected; choosing none is valid.
- A new `/github-setup` command whose prompt drives Claude to generate the
  hooks, the selected workflows, issue templates and PR template for the
  current project.
- `init` offers to start that session as a step, the same way it offers the
  roadmap session.
- Two core skills (installed in every setup, `metadata.core: true`):
  - `github-actions` (exists; becomes core);
  - `git-hooks` (new).
- Reference templates live inside the skills, per stack (Node, Python, Go):
  hook scripts, `lefthook.yml`, CI workflow, dependabot, issue forms, PR
  template. Claude adapts them; it does not copy them blindly.
- Local CI is part of the installed harness: `.claude/tools/workflows.mjs`
  (already installed) plus a `.claude/scripts/ci-local.sh` wrapper usable in
  any stack.

## Non-goals

- The CLI rendering hooks or workflows itself (no template engine in `cli/`).
- CI for the ai-stones repository itself. This repo has no workflows.
- Deploy workflows: too project-specific for a template; the `github-actions`
  and `ci-cd` skills cover them when asked.
- Installing lefthook, act or Docker for the user.

## Anti-goals

- Hooks so slow that people bypass them with `--no-verify`. Pre-commit stays
  fast (format/lint on staged files); slow suites go in pre-push or CI.
- Hooks or workflows that run commands the project doesn't have.
- Generating a workflow the user didn't select.
- Overwriting a project's existing hooks, workflows or templates without
  asking.

## Current state (what this changes)

- Commit `281b455` moved this repo's `.github/` to `github/`. GitHub no longer
  runs this repo's CI, and `npm run ci:local` finds no workflows
  (`tools/workflows.mjs` reads `.github/workflows`).
- `github/workflows/*.yml` and `github/dependabot.yml` are this repo's own
  pipeline, not templates.
- `github/hooks/*` are empty files; `github/templates/` is empty and untracked.
- `cli/install.mjs` installs nothing from `github/`; `package.json` doesn't
  ship it.
- `github-actions` is installed only when `.github/workflows` is detected
  (asserted in `cli/stones.test.mjs`).

## Approaches

1. **CLI generates the files from per-stack templates.** Deterministic, works
   right after `init`, but a template per stack to maintain and no adaptation
   to unusual projects.
2. **CLI copies generic starters; Claude adapts later.** Little to maintain,
   but the harness isn't usable until someone adapts it.
3. **Claude generates them in a session started by `init`, using core skills
   that carry the reference templates.** *Chosen.* Fits how ai-stones already
   starts the roadmap session, adapts to the real stack and commands, and the
   same command can be rerun later.

Hook activation (inside approach 3): the `git-hooks` skill teaches both
mechanisms. Claude uses lefthook when the project already has it or it is on
PATH; otherwise plain scripts in `.githooks/` activated with
`git config core.hooksPath .githooks`. *Builder's call, approved by the user.*

## Design

### Repository moves

- `github/` is removed entirely, including this repo's own `ci.yml`,
  `devcontainers.yml`, `release.yml`, `dependabot.yml` and `.actrc`. The
  repository has no CI; checks run locally with `npm run check`, `npm test`
  and `npm run smoke`.
- Template content moves into the skills' reference folders.
- `ci:local` and `ci:local:list` npm scripts are removed from `package.json`.
  README drops "Run the CI workflow locally" and the CI badge, and documents
  `.claude/scripts/ci-local.sh` for user projects.

### Skills

`skills/git-hooks/` (new, core):

- `SKILL.md`: which hook does what (pre-commit: format + lint, staged files;
  commit-msg: conventional commits if the project uses them; pre-push: tests
  + typecheck; post-merge/post-checkout: dependency reinstall reminder), speed
  budget, choosing lefthook vs `core.hooksPath`, never clobbering existing
  hooks, how to verify a hook actually runs.
- `templates/`: `lefthook.yml` and `.githooks/*` scripts for node, python, go,
  using the project's commands as placeholders Claude fills in.

`skills/github-actions/` (existing, gains `metadata.core: true`):

- `templates/`: per catalog entry and stack — `ci-{node,python,go}.yml`,
  `release-{node,python,go}.yml`, `security.yml`, `dependabot.yml`,
  `ISSUE_TEMPLATE/bug_report.yml`, `ISSUE_TEMPLATE/feature_request.yml`,
  `ISSUE_TEMPLATE/config.yml`, `pull_request_template.md`.
- `SKILL.md` gains a short section pointing at the templates and requiring a
  local act run (via the workflows tool) before calling a workflow done.

Making `github-actions` core changes the detection test in
`cli/stones.test.mjs` (it is now always included).

### Command

`commands/github-setup.md`, installed like `roadmap.md`. The prompt tells
Claude to:

1. Read `AGENT.md`, the stack, and the commands from `.claude/settings.json` /
   the project manifests. List what already exists under `.github/`,
   `.githooks/`, `lefthook.yml`, `.git/hooks`.
2. Tell the user in a few lines what it will create and what it will leave
   alone; ask before replacing anything existing.
3. Generate hooks with the `git-hooks` skill and activate them; prove one runs.
4. Generate only the selected workflows (passed in the prompt; if none were
   selected, skip this step) with the `github-actions` skill; run
   `.claude/tools/workflows.mjs list`, then offer a local run (the tool's own
   confirmation applies). Run with no selection (e.g. `/github-setup` typed by
   hand), it asks which catalog entries to generate.
5. Generate the issue templates and PR template.
6. Summarise what was created and how to rerun it.

### CLI

- `cli/questions.mjs`: a multi-select `github.workflows` question with the
  catalog above, default empty, saved in answers like other selections.
  Hooks, issue templates and PR template are always part of the step.

- `cli/github-setup.mjs`: `githubSetupPrompt(target)` and
  `startGithubSetupSession(target, { workflows })`, mirroring `cli/roadmap.mjs` (installed
  command preferred over package copy; same "Claude not on PATH" fallback).
- `bin/stones.mjs`: `init` offers the GitHub setup session after install and
  before the roadmap offer; `--no-github-setup` skips it; non-interactive runs
  print the "Next:" hint. New subcommand `npx ai-stones github-setup [dir]`.
  `--print-prompt` applies to it as well.

### Local CI script

`scripts/ci-local.sh` in the package → installed to
`.claude/scripts/ci-local.sh`: a thin wrapper around
`node .claude/tools/workflows.mjs "$@"` with `run` as the default subcommand,
checking that `act` and Docker are available first. Added to
`package.json` `files`; `npm run check` runs shellcheck on it when
shellcheck is installed.

## Testing

- Unit tests for `cli/github-setup.mjs` (prompt resolution, selected workflows
  in the prompt, none selected, missing-Claude fallback), mirroring the
  roadmap tests.
- The workflows question defaults to none and saves the selection.
- `cli/stones.test.mjs`: `github-actions` and `git-hooks` are always in the
  installed skills; `github-setup.md` and `ci-local.sh` are installed.
- `scripts/smoke.mjs`: `init --yes` on the sample projects installs the
  command, skills and script.
- `npm run check`, `npm test` and `npm run smoke` pass; `npm run check` no
  longer expects `.github/` or `.actrc`.

## Left to the builder

- Exact wording of the skills and the command prompt.
- Template details per stack (which actions, versions pinned by SHA,
  Python tool — uv vs pip — chosen to match `ci-python.yml` to detection).
- Whether `ci-local.sh` also exposes `list`/`status` shortcuts.
