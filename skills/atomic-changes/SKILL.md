# Atomicity and Danger Zones

One purpose per commit, branch and pull request. Database, dependency and external-communication changes (danger zones) go on their own specced branch and PR. The `atomicity` hook enforces this on `git commit`, `git push` and `gh pr create`.

## Principles

- One logical change per commit. Every commit builds and passes tests on its own.
- One purpose per branch, one story per PR.
- Never bundle a danger-zone change with anything else.
- Migrations are generated by the stack's generator, never hand-written.
- A danger-zone branch carries a written spec before it is committed, pushed or opened as a PR.

**REQUIRED SUB-SKILLS:** `creating-branches` for naming, splitting and stacking branches; `opening-pull-requests` for PR order and description.

## Danger zones

Each changed file gets one class. Precedence: `db` > `packages` > `network` > `neutral` > `code`.

| Zone | Branch prefix | What counts |
|---|---|---|
| `db` | `db/` | Migration directories, schema files (`schema.prisma`, `*.sql`, `db/schema.rb`), seeds and backfills, ORM model/entity sources the generator reads. |
| `packages` | `deps/` | Manifests and lockfiles (`package.json`, `*-lock.*`, `requirements*.txt`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile*`...). `package.json`, `pyproject.toml`, `Cargo.toml` count only when a dependency section changes; a scripts or tool-config change is plain code. |
| `network` | `net/` | Talking to other hosts: absolute external `http(s)://` / `ws(s)://` URLs, third-party SDK imports (`stripe`, `@aws-sdk/*`, `openai`, `nodemailer`...), raw sockets, new `*_URL` / `*_HOST` / `*_ENDPOINT` / `*_API_KEY` env reads, config pointing at them (`.mcp.json`, sandbox network settings, proxy config). |

- `neutral`: tests, fixtures, mocks, docs (`*.md`) and spec files. They may ride along with any zone, so a `net/` PR can carry its tests.
- `code`: everything else.

Not network: relative URLs (`fetch('/api/x')`), `localhost`, `127.0.0.1`, `*.local`, `example.com`, client calls with a variable argument, XML namespaces and JSON schema ids, `package.json` metadata (`homepage`, `repository`...), comment-only lines, incoming routes (unless `network.incoming` is `true`), and hosts listed in `zones.network.allowHosts`. Only added lines of non-neutral files are content-checked. A block names `<file>: <line>` for what triggered it.

## Rules

Every block starts with `Atomicity guard (R<n>):`, names the files and gives the next command.

| Rule | Blocks | Fix |
|---|---|---|
| R1 | A commit whose staged set (plus `-a`, pathspecs, chained `git add`) mixes two zones, or a zone with `code`. | Unstage all but the zone you keep (`git restore --staged <files>`, or `git rm --cached <files>` before the first commit). Drop files from a chained `git add` that the block lists separately. Commit the rest separately. |
| R2 | A danger commit on the default branch or a branch without the matching prefix; a branch that mixes zones vs its base. | `git switch -c db/<name>` (or `deps/`, `net/`), or move stray changes: `git switch -c <prefix><name> <base>`, then cherry-pick. |
| R3 | A danger branch whose spec is missing, has a missing/empty section, a wrong `## Zone`, or placeholder text. | Copy [spec-template.md](spec-template.md) to `.claude/danger/<branch with / as -->.md`, fill every section, `git add` it. |
| R4 | Writes into a migration directory; any agent write to `.claude/atomicity.json`. | Edit the schema/model source, then run the generator the block prints. For the config file: ask the user. |

If R4 says no migration generator is configured — set `migrations.generate`, or set `migrations.allowEdits: true` for tools whose migrations are hand-written (golang-migrate, Flyway, dbmate, goose). Only a human edits `.claude/atomicity.json`.

## Migrations

Edit the model or schema, then run the generator (for example `npx prisma migrate dev --name <name>`). Model and schema files stay editable; only migration directories are protected. A human may allow hand edits (a data backfill) with `migrations.allowEdits`.

## Never

- Never work around a block (`HUSKY=0`, `env git`, wrappers, splitting a command to dodge the check). The hook sees through them; fix the change instead.
- Never edit `.claude/atomicity.json` or add a branch to `exempt` yourself. Ask the user.
- Never hand-write a migration to save time.

How the hook parses commands, judges bases and stacked branches, and the full config keys: [hook-reference.md](hook-reference.md).
