# The 4D Framework for AI-Assisted Software Engineering

## Delegation · Description · Discernment · Diligence

**Purpose:** A practical framework for using AI systems in software
engineering, code generation, debugging, refactoring, code review, and
testing.

The 4D framework treats AI-assisted development as an engineering
discipline rather than a prompt-writing exercise. Its objective is to
improve delivery speed without sacrificing correctness, maintainability,
security, reliability, or human accountability.

> **Core principle:** Delegate execution where AI adds leverage, provide
> enough engineering context to constrain its work, evaluate its outputs
> with evidence, and retain human responsibility for consequential
> decisions.

The dimensions form a continuous loop:

1.  Understand the engineering problem and allocate responsibilities.
2.  Describe the task and establish a shared technical context.
3.  Generate, inspect, execute, and evaluate the result.
4.  Secure, document, approve, and monitor the change.
5.  Feed failures and lessons back into the next iteration.

AI output is a proposed change, not proof that the task is complete.

# 2. Delegation: Allocate engineering work deliberately

**Central question: Which parts of the engineering task should be
performed by AI, by an engineer, or collaboratively?**

Delegation begins with understanding the problem. Do not start by asking
a model to implement a solution before establishing what needs to change
and why.

## 2.1 Understand the engineering problem

Before delegating, identify:

- **Problem:** What is broken, missing, slow, insecure, or difficult
  to maintain?
- **Objective:** What observable outcome should the change produce?
- **Scope:** Which services, modules, APIs, data models, or workflows
  are affected?
- **Current behavior:** What does the system do today?
- **Expected behavior:** What should it do after the change?
- **Dependencies:** Which components, contracts, libraries, services,
  or teams are involved?
- **Constraints:** What architectural, performance, security,
  compatibility, or operational rules apply?
- **Risk:** What is the impact if the proposed change is wrong?

Distinguish symptoms from root causes. A stack trace may identify where
a failure surfaced, not where it originated.

## 2.2 Decide what to delegate

AI is often useful for work that involves exploration, transformation,
drafting, or repetitive implementation. Human engineers remain
responsible for product intent, architecture, risk decisions, and
acceptance.

A useful rule is:

- **Delegate drafts and bounded execution.**
- **Collaborate on investigation and design.**
- **Retain human ownership of requirements, risk acceptance, and

Do not assume that AI-generated code is safe to merge or deploy without
review.

## 2.3 Decompose work into bounded tasks

Large engineering requests should be split into units that can be
understood, implemented, and verified independently.

For example, implementing tenant-aware database access:

1.  Inspect the existing tenant resolution flow.
2.  Identify how database connections are created and reused.
3.  Trace authentication and tenant identity propagation.
4.  Define isolation invariants.
5.  Propose the smallest compatible design.
6.  Implement the connection-resolution change.
7.  Add unit tests for connection selection.
8.  Add integration tests for cross-tenant isolation.
9.  Run relevant regression tests.
10. Document configuration and operational implications.

Each task should have a clear input, expected output, constraints, and
completion criteria.

Avoid broad instructions such as "fix the database architecture" when a
sequence of smaller tasks is possible.

## 2.4 Establish success and failure criteria before implementation

Define acceptance criteria before asking AI to write code.

Example:

**Success criteria** - Requests resolve the correct tenant. -
Connections are reused only within the intended isolation boundary. -
Concurrent requests cannot cross tenant boundaries. - Existing API
contracts remain compatible. - Unit and integration tests pass. - No new
critical security issue is introduced.

**Failure criteria** - Tenant identity can be supplied or overridden by
an untrusted client. - A connection is shared across tenants. - Missing
tenant context silently falls back to a default tenant. - Existing
behavior regresses. - Tests do not exercise concurrent or cross-tenant
scenarios.

A task is not complete merely because the code compiles or the model
reports success.

## 2.5 Select models and tools based on the workload

Choose a model using representative engineering tasks rather than
reputation alone.

Typical task-to-capability mapping:

- Small transformations and boilerplate: prioritize speed and cost.
- Debugging complex interactions: prioritize reasoning and repository
  understanding.
- Code generation: prioritize correctness, language proficiency, and
  test performance.
- Code review: prioritize defect detection, context awareness, and
  precision.
- Large refactors: prioritize context handling, tool use, and
  regression discipline.

A model that generates code cheaply but requires extensive correction
may have a higher total engineering cost.

## 2.6 Decide when not to delegate

Use additional human control when:

- Requirements are unclear or disputed.
- The change affects authentication, authorization, cryptography, or
  tenant isolation.
- The operation can delete or irreversibly modify data.
- The change affects financial, safety-critical, or regulated
  workflows.
- The model lacks access to the required source of truth.
- The proposed change crosses architectural boundaries that are not
  understood.
- The engineer cannot independently evaluate the result.

# 3. Description: Give AI the engineering context and instructions it needs

**Central question: How do we translate an engineering objective into
precise, actionable instructions?**

Prompt engineering for software development is primarily context
engineering plus task specification. The model needs to understand the
repository, existing conventions, expected behavior, and the boundaries
of the requested change.

## 3.1 Build a shared engineering context

Provide the smallest sufficient set of information that materially
affects the implementation.

### Project context

- Product and service purpose.
- Language, framework, runtime, and major dependencies.
- Repository structure and relevant modules.
- Architectural style and established patterns.
- Relevant API and data contracts.

### Task context

- Problem statement.
- Current behavior.
- Expected behavior.
- Relevant source files, logs, stack traces, or failing tests.
- Steps already attempted.
- Previous decisions that constrain the solution.

### Engineering constraints

- Compatibility requirements.
- Coding standards and naming conventions.
- Module and dependency boundaries.
- Security and privacy requirements.
- Performance and scalability requirements.
- Migration and deployment constraints.
- Dependencies that must not be added or changed.

Do not dump the entire repository into every prompt. Identify the files
and contracts that are relevant, then expand context when investigation
shows it is necessary.

## 3.2 Use a consistent prompt structure

A robust engineering prompt can use the following sections:

1.  **Role:** The engineering perspective or expertise required.
2.  **Objective:** The outcome to achieve.
3.  **Repository context:** Relevant architecture, files, and
    conventions.
4.  **Current behavior:** What happens now, including evidence.
5.  **Expected behavior:** What should happen.
6.  **Instructions:** The work sequence or requested deliverables.
7.  **Constraints:** What must and must not change.
8.  **Acceptance criteria:** How completion will be judged.
9.  **Validation:** Tests, commands, and checks required.
10. **Uncertainty handling:** What to do when information is missing or
    contradictory.

Not every task needs all ten sections. Use the level of structure that
matches the task's complexity and risk.

## 3.3 Define the role without relying on role-play

A role can establish a useful technical perspective, but it does not
guarantee expertise.

Example:

```text
Act as a senior backend engineer experienced in
NestJS, TypeScript, PostgreSQL, distributed systems,
and production operations.

Review the existing implementation before proposing
changes. Follow established repository conventions.
Prefer the smallest maintainable change that satisfies
the requirements.
```

The repository evidence and explicit constraints matter more than an
impressive role description.

## 3.4 Specify the expected deliverable

Be explicit about what the AI should return or change.

Examples:

- Root-cause analysis with evidence.
- Implementation plan with alternatives and trade-offs.
- A focused source-code change.
- Unit and integration tests.
- A code-review report with severity and file references.
- A migration plan with rollback considerations.
- Updated API documentation.
- A test report listing commands, results, and unresolved failures.

Also specify whether the model should inspect first, propose a plan,
wait for approval, or implement immediately.

## 3.5 Define repository and change boundaries

For code-generation tasks, explicitly state:

- Which files or modules may be changed.
- Which interfaces and contracts must remain stable.
- Which dependencies may be added.
- Which generated files must not be edited manually.
- Whether database schema changes are permitted.
- Whether public API behavior may change.
- Whether formatting or unrelated refactoring is out of scope.

Example:

```text
Change boundaries:
- Keep the existing module structure.
- Do not introduce cross-module entity imports.
- Do not change public API response shapes.
- Do not add dependencies without explaining why.
- Do not modify unrelated files.
- Do not alter database schema unless required and approved.
```

## 3.6 Define good and bad examples

Examples help communicate the expected level of implementation quality.

**Good instruction**

```text
Implement a tenant-aware repository lookup.

Requirements:
- Resolve tenant identity from the authenticated
  request context, not from an untrusted request body.
- Reuse connections only for the same tenant.
- Fail explicitly when tenant context is missing.
- Preserve existing repository interfaces.
- Add tests for missing tenant context, connection
  reuse, concurrent requests, and cross-tenant isolation.
```

**Weak instruction**

```text
Make the database work for multiple tenants.
```

The weak instruction leaves behavior, boundaries, security, and
validation undefined.

For recurring tasks, maintain examples of:

- Accepted implementations.
- Rejected implementations.
- Expected test cases.
- Error-handling conventions.
- API response formats.
- Architectural patterns.

## 3.7 Ask for useful explanations and evidence

Do not require the model to reveal private internal reasoning. Ask for
concise, inspectable engineering evidence.

Prefer:

```text
Before implementation:
1. Summarize the relevant existing behavior.
2. Identify dependencies and constraints.
3. List assumptions and missing information.
4. Compare viable approaches and their trade-offs.
5. Recommend the smallest suitable change.

After implementation:
1. Summarize changed files and behavior.
2. Explain important design decisions.
3. List tests and commands executed.
4. Report actual test results.
5. Identify limitations and unresolved risks.
```

This makes the work auditable without requiring hidden chain-of-thought
disclosure.

## 3.8 Use an investigation-first workflow for uncertain tasks

When the task involves an unfamiliar codebase, a production bug, or a
complex architectural change, separate investigation from
implementation.

**Phase A --- Investigation** - Inspect relevant files. - Trace
execution paths. - Reproduce the failure if possible. - Identify
evidence and hypotheses. - Report missing information.

**Phase B --- Proposal** - Explain the likely root cause. - Compare
possible fixes. - Identify risks and affected components. - Define tests
and acceptance criteria.

**Phase C --- Implementation** - Make the approved, bounded change. -
Follow repository conventions. - Avoid unrelated modifications.

**Phase D --- Verification** - Run targeted tests. - Run relevant
regression tests. - Inspect the diff. - Report failures honestly.

This avoids allowing an early, unverified assumption to determine the
implementation.

## 3.9 Treat prompts as versioned engineering artifacts

For repeated or production use, manage prompts like code.

Track: - Prompt identifier and version. - Intended task and model. -
Input and output schemas. - Examples and evaluation dataset. - Model
parameters where applicable. - Known limitations. - Evaluation
results. - Change history.

Use prompt variations and A/B testing to compare measurable outcomes. Do
not accept a prompt change solely because one response looks better.

# 4. Discernment: Evaluate generated code and engineering decisions

**Central question: How do we determine whether AI-generated code is
correct, maintainable, secure, and appropriate for the existing
system?**

A convincing explanation is not proof of a correct implementation.
Generated code must be evaluated against requirements, repository
contracts, runtime behavior, and tests.

## 4.1 Evaluate the output across engineering dimensions

---

Dimension Questions

---

Functional correctness Does the code implement the
required behavior?

Requirement alignment Does it satisfy every explicit
acceptance criterion?

Completeness Are edge cases, errors, and
dependencies handled?

Type and contract correctness Are interfaces, schemas, and API
contracts respected?

Architectural consistency Does it follow module boundaries
and established patterns?

Maintainability Is it understandable, cohesive, and
reasonably simple?

Security Does it introduce vulnerabilities
or weaken controls?

Performance Are queries, allocations, network
calls, and algorithms appropriate?

Reliability Does it handle failures, retries,
concurrency, and partial states?

Testability Can behavior be tested
deterministically?

Documentation Are important behavior and
operational changes documented?

---

These dimensions are related but not interchangeable. Code can compile
while violating business rules, security boundaries, or architectural
constraints.

## 4.2 Inspect the implementation, not only the explanation

Review:

- The actual diff.
- Every modified file.
- New dependencies.
- Public interfaces and contracts.
- Database queries and migrations.
- Error handling.
- Logging and sensitive data exposure.
- Concurrency and transaction behavior.
- Configuration and environment changes.
- Test quality and test coverage.

Ask:

- Does the code solve the original problem?
- Is the implementation consistent with neighboring code?
- Does it introduce unnecessary abstractions?
- Are there hidden side effects?
- Can the change break existing callers?
- Are failures handled explicitly?
- Is the solution simpler than the alternatives?

## 4.3 Recognize common AI-generated code failures

---

Failure pattern Engineering manifestation

---

Hallucinated APIs Uses methods, options, or library
features that do not exist

Incorrect assumptions Infers behavior from incomplete
repository context

Interface drift Changes contracts unexpectedly

Overengineering Adds abstractions and dependencies
without need

Underengineering Omits validation, error handling,
or edge cases

Insecure defaults Trusts user input, exposes secrets,
or weakens access control

Concurrency defects Introduces races, unsafe shared
state, or incorrect locking

Data integrity defects Breaks transaction boundaries or

Test theater Generates tests that pass without
validating meaningful behavior

changes unrelated behavior

False completion Claims tests passed without
executing them

---

## 4.4 Evaluate the proposed approach

Before accepting a solution, assess:

**Technical validity** - Are the APIs and libraries used correctly? -
Does the code compile against the installed versions? - Are the
algorithms and data structures appropriate? - Are database operations
correct?

**Architectural validity** - Does the solution respect module
ownership? - Does it preserve dependency direction? - Does it avoid
unnecessary coupling? - Does it fit the deployment model?

**Operational validity** - Can it be configured and deployed? - Are
migrations safe? - Is rollback possible? - Are logs and metrics
sufficient? - Are failure modes understood?

**Security validity** - Are authorization and authentication enforced? -
Is input validated? - Are secrets protected? - Are tenant boundaries
preserved? - Are external calls and tool permissions constrained?

## 4.5 Evaluate feedback quality

A useful correction should identify:

1.  The defect.
2.  The evidence.
3.  The violated requirement or invariant.
4.  The required correction.
5.  The test that will demonstrate the correction.

Example:

```text
Defect:
The repository resolves a database connection using
a tenant identifier supplied in the request body.

Why this is incorrect:
The request body is not a trusted source of tenant
identity. This can allow tenant-context manipulation.

Required correction:
Resolve tenant identity from the authenticated
request context and enforce the tenant isolation
invariant at the repository boundary.

Required validation:
Add integration tests proving that a user authenticated
for tenant A cannot read or modify tenant B's records.
```

Feedback should be specific, evidence-based, and testable.

# 5. Diligence: Make AI-assisted engineering safe and accountable

**Central question: What controls ensure that AI-generated changes can
be trusted, reviewed, maintained, and safely delivered?**

Diligence turns evaluation into engineering controls. It ensures that
defects are detected before they reach users or production systems.

## 5.1 Treat generated code as an untrusted contribution

Apply the same engineering standards to AI-generated code as to
human-written code.

Before accepting a change:

- Inspect the diff.
- Confirm the change is within scope.
- Verify dependencies and licenses where relevant.
- Run formatting, linting, and type checks.
- Run targeted tests.
- Run regression tests.
- Perform security checks appropriate to the change.
- Review migrations and data-loss risks.
- Confirm documentation and operational changes.
- Obtain required human approval.

Never merge or deploy solely because an AI assistant says the
implementation is complete.

## 5.2 Apply risk-based review

The level of oversight should match the potential impact.

---

Risk Examples Controls

---

Low Comments, formatting, Basic review and
isolated documentation formatting checks

Medium Business logic, API Code review, unit
handlers, internal tests, integration
refactors tests

High Authentication, Expert review, security
authorization, tenant tests, integration
isolation, payment tests, explicit

Critical Destructive migrations, Independent
production data verification, backups,
deletion, irreversible approval gates,
operations rollback or recovery
plan

---

A high aggregate quality score cannot compensate for a critical security
or data-integrity failure.

## 5.3 Protect secrets, data, and repository access

For AI coding tools and agents:

- Do not expose credentials, private keys, or production secrets.
- Use least-privilege repository and environment access.
- Separate development, staging, and production permissions.
- Avoid providing production data when synthetic or sanitized data is
  sufficient.
- Treat repository content and external documents as potentially
  untrusted input.
- Review shell commands before execution.
- Require explicit approval for destructive or production-impacting
  operations.
- Keep sensitive information out of prompts, logs, and generated
  artifacts.

Prompt injection can occur through source files, issue descriptions,
documentation, logs, and other content read by an AI agent. Retrieved
content should not automatically be treated as trusted instructions.

## 5.4 Maintain traceability

For significant AI-assisted changes, record:

- Task or issue identifier.
- Prompt and relevant context version.
- Model and tool configuration where useful.
- Files changed.
- Human reviewer and approver.
- Tests and commands executed.
- Test results.
- Known limitations.
- Deployment and rollback information.

The purpose is not to log every conversational detail. It is to preserve
enough evidence to understand, reproduce, review, and investigate
important changes.

## 5.5 Preserve human accountability

Define ownership explicitly:

Responsibility Accountable party

---

Product requirements Product owner / requester
Technical direction Engineering owner
AI prompt and tool configuration AI engineer / developer
Implementation review Assigned engineer
Security assessment Security owner or qualified reviewer
Test acceptance Engineering team
Release approval Authorized release owner
Production incident response Service owner / operations

AI can assist with every stage, but it does not replace the people
accountable for the software.

# 6. Testing principles for AI-generated code

Testing is the most important bridge between generated code and
engineering confidence.

A model's explanation, confidence, or self-assessment is not a
substitute for executable verification.

Use a layered testing strategy.

## 6.1 Define tests from requirements, not from generated code

A common failure is allowing the model to write an implementation and
then generate tests that merely confirm its own assumptions.

Instead:

1.  Define requirements and expected behavior independently.
2.  Identify invariants and failure scenarios.
3.  Write acceptance criteria.
4.  Create representative test cases.
5.  Generate or implement the solution.
6.  Execute the tests against the implementation.

Where possible, derive expected outcomes from specifications, domain
rules, existing behavior, and independent test oracles.

## 6.2 Apply the testing pyramid

---

Testing level What it verifies Examples

---

Static checks Structural and TypeScript compiler,
language-level ESLint, formatting,
correctness static analysis

validators, domain
logic

authentication

Contract tests Compatibility between API schemas, events,
components service interfaces

End-to-end tests User-visible workflows Registration, checkout,
reservation, payment

Security tests Resistance to misuse Authorization,
and vulnerabilities injection, tenant
isolation

Performance tests Behavior under load Throughput, latency,
concurrency, resource
usage

Human acceptance Business and Domain review,
operational suitability usability, release
approval

---

Use the appropriate levels for the change. A documentation-only change
does not need the same testing effort as a database isolation change.

## 6.3 Test normal, boundary, and failure conditions

For every important behavior, consider:

**Happy paths** - Valid input. - Expected permissions. - Normal
dependencies. - Successful external calls.

**Boundary cases** - Empty input. - Minimum and maximum values. - Large
payloads. - Duplicate records. - Concurrent requests. - Missing optional
fields.

**Failure cases** - Invalid input. - Missing authorization. - Database
unavailable. - Timeout. - Partial failure. - Duplicate event delivery. -
External service errors. - Retry exhaustion.

**Adversarial cases** - Malformed input. - Injection attempts. -
Privilege escalation. - Cross-tenant access. - Unexpected content. -
Resource exhaustion.

## 6.4 Use property-based and invariant testing

Example-based tests are necessary but may miss combinations of inputs.

Property-based testing checks general properties across many generated
inputs.

Examples:

- A normalized email should remain normalized after repeated
  normalization.
- A tenant-scoped lookup must never return another tenant's records.
- A pagination operation must not return duplicate records across
  non-overlapping pages.
- A retry-safe operation must not create duplicate business effects.
- Serialization followed by deserialization should preserve the
  supported data.

Invariants are especially valuable for security and data integrity
because they express what must always remain true.

## 6.5 Test migrations and data changes independently

For database changes:

- Test migration from the previous supported schema.
- Test migration on representative data.
- Check constraints and indexes.
- Verify data preservation.
- Test rollback or documented recovery procedures.
- Measure potentially expensive operations.
- Confirm compatibility between application versions and schema
  versions.
- Verify behavior with concurrent application instances where
  relevant.

Never treat a generated migration as safe merely because the ORM created
it successfully.

## 6.6 Test the tests

AI-generated tests can be misleading.

Check that tests:

- Assert meaningful behavior.
- Fail when the implementation is deliberately broken.
- Exercise the actual code path.
- Use realistic fixtures.
- Avoid excessive mocking.
- Verify error paths and side effects.
- Do not depend on execution order.
- Are deterministic and isolated.
- Clean up resources.
- Do not silently skip important assertions.

Useful techniques include mutation testing, fault injection, and
deliberately introducing defects to verify that tests detect them.

## 6.7 Use regression testing

Every code change should be evaluated against previously working
behavior.

Maintain a regression suite covering:

- Core business workflows.
- Public APIs and contracts.
- Authentication and authorization.
- Database invariants.
- Known historical defects.
- Critical integrations.

For AI-generated changes, regression testing is particularly important
because a model may make a locally correct change that breaks a distant
dependency.

## 6.8 Verify test claims with actual execution evidence

Distinguish these statements:

- "Tests were generated."
- "Tests were inspected."
- "Tests were executed."
- "Tests passed."
- "Tests passed in the target environment."

They are not equivalent.

A completion report should include the exact commands executed, relevant
results, failures, and checks that were not performed.

# 7. An engineering evaluation rubric

Use a task-specific rubric to make code evaluation more consistent.
Scores should support judgment, not replace mandatory engineering gates.

## 7.1 Suggested dimensions and weights

Dimension Suggested weight

---

Functional correctness 20%
Requirement alignment 15%
Test quality and coverage 15%
Security and data integrity 15%
Architectural consistency 10%
Maintainability 10%
Reliability and error handling 5%
Performance 5%
Documentation and traceability 5%
**Total** **100%**

Score each dimension from 1 to 5:

- **1 --- Unacceptable:** Major defects or unmet requirements.
- **2 --- Weak:** Significant gaps; substantial rework required.
- **3 --- Acceptable:** Meets basic expectations with known
  limitations.
- **4 --- Good:** Meets requirements with minor issues.
- **5 --- Excellent:** Strong, well-verified implementation.

### Mandatory rejection conditions

Reject or block a change regardless of its aggregate score if it:

- Violates a critical security invariant.
- Allows unauthorized access or cross-tenant data leakage.
- Causes unacceptable data loss or corruption.
- Breaks a mandatory API or data contract.
- Fails a required acceptance test.
- Contains unreviewed destructive production operations.
- Makes unsupported claims about validation or test results.

Weights should be adjusted by task type. Security-sensitive work should
have stricter security gates than a routine UI text change.

# 8. End-to-end workflow for AI-assisted software engineering

This workflow combines all four dimensions into a repeatable development
process.

## Phase 1 --- Understand and delegate

1.  Identify the actual problem.
2.  Define the desired outcome.
3.  Establish scope and constraints.
4.  Identify dependencies and risks.
5.  Decide which work can be delegated.
6.  Define success and failure criteria.

**Deliverable:** A bounded engineering task.

## Phase 2 --- Describe and prepare context

1.  Identify relevant repository files.
2.  Explain the existing architecture and conventions.
3.  Provide current and expected behavior.
4.  Define interfaces and constraints.
5.  Specify the required output.
6.  Establish acceptance criteria and validation commands.
7.  Identify missing information.

**Deliverable:** An actionable engineering prompt.

## Phase 3 --- Investigate and design

1.  Inspect the existing implementation.
2.  Trace relevant dependencies.
3.  Reproduce the issue when possible.
4.  Identify evidence and assumptions.
5.  Compare implementation options.
6.  Select the smallest suitable approach.
7.  Identify required tests.

**Deliverable:** A technical proposal or implementation plan.

## Phase 4 --- Generate and implement

1.  Implement the approved change.
2.  Follow repository conventions.
3.  Keep the diff focused.
4.  Add or update tests.
5.  Update documentation where necessary.
6.  Avoid unrelated refactoring.

**Deliverable:** A reviewable code change.

## Phase 5 --- Verify and discern

1.  Inspect the diff.
2.  Run formatting and lint checks.
3.  Run type checking and static analysis.
4.  Execute unit tests.
5.  Execute integration and contract tests where relevant.
6.  Run regression tests.
7.  Review security and performance implications.
8.  Compare results against acceptance criteria.
9.  Report unresolved issues.

**Deliverable:** Evidence-backed verification results.

## Phase 6 --- Approve and deliver

1.  Complete human code review.
2.  Confirm required approvals.
3.  Verify migrations and deployment requirements.
4.  Document risks and rollback procedures.
5.  Merge and deploy through established controls.
6.  Monitor production behavior.

**Deliverable:** An approved and traceable engineering change.

## Phase 7 --- Learn and improve

1.  Record defects and failure patterns.
2.  Identify whether failures originated in requirements, context,
    prompting, model behavior, implementation, or testing.
3.  Improve prompts and examples.
4.  Expand regression datasets.
5.  Reevaluate model and tool choices.
6.  Update engineering guidelines.

**Deliverable:** An improved AI-assisted development process.

# 10. Practical engineering checklist

Use this checklist before accepting an AI-assisted code change.

## Delegation

- [ ] Is the problem clearly understood?
- [ ] Is the scope bounded?
- [ ] Are dependencies identified?
- [ ] Are human responsibilities clear?
- [ ] Are success and failure criteria defined?
- [ ] Is the model appropriate for the task?

## Description

- [ ] Has relevant repository context been provided?
- [ ] Are current and expected behaviors clear?
- [ ] Are constraints and contracts explicit?
- [ ] Are change boundaries defined?
- [ ] Are acceptance criteria testable?
- [ ] Are uncertainty-handling instructions included?

## Discernment

- [ ] Does the implementation satisfy the requirements?
- [ ] Does it follow architectural conventions?
- [ ] Are edge cases handled?
- [ ] Are security and data-integrity implications reviewed?
- [ ] Are tests meaningful and sufficient?
- [ ] Have unsupported claims and assumptions been challenged?
- [ ] Is the diff limited to the intended scope?

## Diligence

- [ ] Have formatting, linting, and type checks been run?
- [ ] Have relevant tests been executed?
- [ ] Have regression tests been considered?
- [ ] Have migrations and destructive operations been reviewed?
- [ ] Are secrets and sensitive data protected?
- [ ] Has a qualified human reviewed the change?
- [ ] Are results and limitations documented?
- [ ] Are approval, deployment, and rollback controls satisfied?

# 11. Final principles

1.  **AI-generated code is a proposal, not an authoritative
    implementation.**
2.  **Requirements and acceptance criteria should exist independently of
    generated code.**
3.  **Repository context is as important as prompt wording.**
4.  **Prefer small, bounded, reviewable changes over broad autonomous
    modifications.**
5.  **Generate tests from requirements, not merely from the
    implementation.**
6.  **Passing tests provide evidence, not a guarantee of correctness.**
7.  **Test the tests, especially when AI generates them.**
8.  **Treat security, authorization, tenant isolation, and data
    integrity as mandatory invariants.**
9.  **Never claim that commands or tests were executed when they were
    not.**
10. **Keep humans accountable for architecture, risk acceptance, and
    production delivery.**
11. **Measure improvements using correctness, defect rates, review
    effort, latency, and cost per accepted change.**
12. **Feed failures back into prompts, evaluation datasets, tooling, and
    engineering practices.**

## The underlying philosophy

**Delegation** determines who should perform the engineering work.

**Description** ensures the AI understands the task, context, and
constraints.

**Discernment** determines whether the generated solution is technically
and functionally sound.

**Diligence** ensures the solution is tested, secure, traceable, and
responsibly delivered.

The objective is not to maximize the amount of code generated by AI. It
is to maximize the amount of **correct, maintainable, secure, and
valuable software delivered with AI assistance**, while preserving
engineering judgment and accountability.
